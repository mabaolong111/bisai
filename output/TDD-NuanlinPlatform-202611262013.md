## 摘要

暖邻平台面向社区居家养老场景，围绕老人本人、家属和社区工作人员三类角色，提供养老资格认证、高龄补贴、居家养老、老年体检、办理进度、期限提醒、资源推荐、探访关怀和社区运营台账等功能。系统采用轻量级单机构架，前端使用原生 HTML、CSS 和 JavaScript，服务端使用 Node.js 内置模块，业务数据以 JSON 文件持久化，无需安装第三方 npm 运行依赖。

系统已实现角色登录、独立账号、服务端权限裁剪、工单状态流转、批量审核、退回留痕、资源上下架与改派、家属三项独立授权、报告和评价管理、退出账号并切换其他账号等能力。老人和家属端保留语音辅助功能；社区端按管理场景移除语音入口，并在居民推荐预览中隐藏距离、朗读和相对位置图。平台目前仍属于本机演示系统，实名、短信、人脸、OCR、补贴支付、卫生报告、真实地图和外部推送均未完成真实服务接入。

# 1 项目概述

## 1.1 建设背景

社区养老服务涉及老人、家属、服务点和社区工作人员等多方主体。传统线下流程容易出现信息分散、代办权限不清、办理进度难跟踪、服务资源更新不及时以及审核过程缺少留痕等问题。暖邻平台通过统一的三端入口和本地化业务流程，将申请、审核、服务、评价、授权和提醒串联起来，为社区养老服务提供可演示、可操作、可验收的一体化原型。

## 1.2 建设目标

1. 建立老人、家属、社区三类角色的独立登录与数据隔离机制。
2. 支撑资格认证、高龄补贴、居家养老和老年体检四类核心业务。
3. 建立从申请、审核、确认、办结到评价或报告录入的可追踪流程。
4. 通过画像和服务需求生成资源推荐，并保证下架资源不再进入推荐和预约。
5. 支持家属在授权范围内代办和查看，健康报告单独授权。
6. 为老人提供大按钮、语音辅助和清晰反馈，为社区提供精简、密集的管理界面。
7. 通过本地持久化、隔离验收和审计留痕提高演示过程的可重复性与可信度。

## 1.3 建设范围

本期范围包括本机网页、Node.js 服务、JSON 数据文件、启动脚本、业务验收脚本和浏览器验收脚本。系统不包含真实支付结算、政府资格认定、医疗机构报告交换、真实地图导航、短信或 App 推送，也不包含公网部署和多节点数据库。

## 1.4 术语说明

| 术语 | 说明 |
| --- | --- |
| 长者档案 | 社区建立的老人基础资料，包括画像、期限、授权和关联账号 |
| 工单 | 一次资格、补贴、居家或体检业务申请及其状态历史 |
| `view` | 家属查看普通进度和探访关怀记录的权限 |
| `proxy` | 家属代办、上传材料、跟踪本人提交工单及评价本人代办服务的权限 |
| `health` | 家属查看体检报告和健康敏感信息的独立权限 |
| 演示资源 | 本地维护的服务点数据，其坐标、距离和费用不代表现实核验结果 |
| 隔离验收 | 使用独立数据文件和随机端口进行测试，避免改写正式业务数据 |

# 2 用户角色与业务需求

## 2.1 角色划分

| 角色 | 主要目标 | 核心能力 | 明确限制 |
| --- | --- | --- | --- |
| 老人端 | 本人办理和查看养老事项 | 四类申请、进度、提醒、画像、家属授权、评价、语音辅助 | 只能操作本人档案和本人工单 |
| 家属端 | 在授权范围内协助长者 | 代办、材料上传、进度跟踪、探访查看、报告查看、本人代办评价 | 受 `view`、`proxy`、`health` 三项独立权限约束 |
| 社区端 | 审核与运营管理 | 档案、账号、工单、资源、探访、期限、预警、统计和审计 | 不提供老人语音播报；不提供通用在线删除工单功能 |

## 2.2 核心用户场景

- 老人本人提交居家陪护申请，选择服务资源、日期和时段，随后查看审核与办结状态。
- 家属获得代办权限后协助长者提交材料，只能跟踪本人账号提交的代办工单。
- 社区工作人员按长者、业务类型和状态筛选工单，执行单笔或批量审核，退回时填写原因。
- 服务资源下架后，推荐和预约入口同步移除该资源，受影响工单需要改派后才能继续办理。
- 老人撤销家属某项权限后，服务端立即按新权限裁剪返回数据，而不是仅隐藏前端按钮。
- 用户点击顶部“退出账号”后，当前会话失效并返回登录页，可重新选择三端之一登录其他账号。

## 2.3 非功能需求

- **易用性：** 老人端采用大入口、明确状态和适老化交互；社区端强调信息密度与工作效率。
- **安全性：** 密码散列、角色校验、服务端数据裁剪、会话过期、登录限速和请求来源检查。
- **可维护性：** 运行文件少、无框架依赖、数据模型集中、业务与验收脚本分离。
- **可恢复性：** 业务数据写入磁盘，保存采用临时文件后重命名，重要人工整理前保留专项备份。
- **可验收性：** 提供独立业务验收和 Edge 浏览器验收，测试不依赖正式业务数据。

# 3 总体技术架构

## 3.1 架构分层

| 层级 | 组成 | 主要职责 |
| --- | --- | --- |
| 表现层 | `yanglao.html`、`app.js`、`style.css` | 三端登录、表单、工作台、角色界面、语音和浏览器图片压缩 |
| 服务层 | `server.js` | 静态资源、会话、权限、业务规则、状态流、推荐、提醒、统计和审计 |
| 数据层 | `nuanlin-data.json` | 长者、账号、工单、资源、探访、核销和审计数据持久化 |
| 启动与运维层 | `start.cmd`、PowerShell、Node 启动器 | Node 检查、端口选择、服务启动、页面打开和停止提示 |
| 验收层 | `tools/acceptance.cjs`、`tools/browser-acceptance.cjs` | API 业务断言、真实浏览器交互、隔离数据和验收报告 |

## 3.2 技术选型及理由

1. **原生前端技术。** 项目规模集中于单页三端演示，原生 HTML/CSS/JavaScript 可以减少构建链路和部署依赖，便于直接审查和修改。
2. **Node.js 内置模块。** 服务端使用 `http`、`fs`、`path` 和 `crypto` 等内置模块，避免额外 npm 运行依赖。
3. **JSON 文件持久化。** 适合本机单进程演示，数据可读、易备份、易构造隔离验收样本；不适合高并发生产环境。
4. **浏览器原生能力。** 使用 Fetch API、Canvas、Web Speech API 和 `localStorage`，实现网络请求、图片压缩、语音辅助和显示设置保存。
5. **同源本机服务。** 页面与 API 由同一 Node 进程提供，避免跨域配置，并通过 Host 和 Origin 检查限制请求来源。

## 3.3 部署形态

服务仅监听 `127.0.0.1`，浏览器通过本机 HTTP 地址访问。默认数据文件位于项目根目录，可通过 `NUANLIN_DATA` 指定其他文件；默认端口为 8765，可通过 `NUANLIN_PORT` 修改。当前没有 HTTPS、反向代理、公网部署或跨设备会话配置。

## 3.4 启动链路与页面路由修复

启动链路为：

1. `start.cmd` 切换到项目目录并调用 `tools/start-project.ps1`。
2. PowerShell 脚本检查 Node.js，要求主版本不低于 22。
3. `tools/launch-project.cjs` 从 8765 开始寻找可用端口，必要时使用后续端口。
4. 启动器调用 `node server.js`，服务就绪后打开 `/yanglao.html`。

本次修复前，实际 HTML 已命名为 `yanglao.html`，但服务端和启动器仍读取 `index.html`，导致启动检查及页面访问失败。当前静态资源映射已统一：

| 请求路径 | 返回文件 |
| --- | --- |
| `/` | `yanglao.html` |
| `/index.html` | `yanglao.html` |
| `/yanglao.html` | `yanglao.html` |
| `/app.js` | `app.js` |
| `/style.css` | `style.css` |

启动器也已改为比较 `yanglao.html` 和 `app.js` 来识别同项目页面，并默认打开 `/yanglao.html`。当前实现没有比较后端构建号，报告不将其描述为完整的健康与版本一致性校验。

# 4 功能模块设计

## 4.1 老人端

老人端首页提供资格认证、高龄补贴、居家养老、体检预约、办理进度和重要提醒六个主要入口。老人可以维护本人画像、提交申请、查看状态历史与退回原因、查看完成说明和服务照片、对已完成居家服务评分，并管理关联家属的三项授权。

老人和家属端保留中文摘要朗读、暂停、继续、重播和语速选择。语音文字指令仅用于辅助打开业务和填写称呼、项目、日期时段及特殊需求；存在歧义时不自动提交，最终仍需用户在表单中核对并明确确认。

## 4.2 家属端

家属端复用业务入口，但权限由服务端决定。`proxy` 控制代办及本人代办记录跟踪，`view` 控制普通进度和探访查看，`health` 单独控制体检报告和健康敏感信息。三项权限互不包含，撤销后立即生效。

未获得健康权限时，体检工单的项目细节会被泛化，报告字段不返回。家属只能评价自己账号提交的已完成代办居家工单，不能评价老人本人或其他家属提交的工单。

## 4.3 社区端

社区端以当前选中长者为中心，提供以下管理能力：

- 多条件工单筛选、单笔审核、批量推进、退回原因和二次确认。
- 使用 `expected` 状态进行乐观并发校验，避免旧页面覆盖他人已更新的状态。
- 长者档案新增与维护、个人期限和其他福利期限配置。
- 老人或家属账号开通、密码重置及旧会话撤销。
- 服务资源新增、编辑、上下架、容量维护和受影响工单改派。
- 居家完成说明、可选照片、体检报告摘要和报告修改历史管理。
- 探访关怀、服务超时预警核销、统计和社区审计台账查看。

社区端没有通用在线删除工单、档案或账号的功能。本次“演示长者工单删除”属于对本地 JSON 数据的人工整理，并保留了专项备份。

## 4.4 推荐、提醒与统计

推荐由服务端根据当前档案、启用资源、演示距离、服务需求、高龄独居和本地演示免费条件计算，前端优先使用服务端推荐结果。演示距离来自示意坐标的数学计算，不是道路距离或真实定位结果。

提醒覆盖个人期限 30/7/1 天及逾期提醒、预约开始 90 分钟后未完成的服务超时提醒。社区统计包括年龄结构、服务需求、补贴状态、办理量、办结量、办结率、工单状态和预警处置情况。

## 4.5 社区端专用界面约束

社区端按管理场景进行了差异化处理：

1. 隐藏“朗读本页摘要”、语音控制、语音助手和动态朗读按钮。
2. `speak()`、语音指令处理和语音识别入口对社区角色直接返回，避免通过脚本绕过界面触发播报。
3. 居民推荐预览和资源详情不显示距离、朗读入口、相对位置图或示意坐标。
4. 社区资源管理区仍保留示意坐标维护能力，因此“隐藏位置”仅限居民推荐预览和资源详情，不代表整个社区后台删除坐标字段。
5. 退出社区账号后清理角色标记，登录页及其他角色不应继承社区样式。

需要特别注意：当前生效 `style.css` 已采用响应式角色字号，社区端为约 14—15.5px 的响应式范围，不再是此前固定 16px；同时当前 `--font-scale` 缺少实际 CSS 消费点，三档字号功能需要重新复核。报告保留这一待办，不沿用历史“固定 16px、三档缩放全部正常”的结论。

# 5 核心业务流程

## 5.1 账号初始化与开通

首次启动且没有社区账号时，服务进程生成随机初始化码，仅用于创建首个社区账号。社区登录后先建立长者档案，再分别开通老人和家属账号。每份档案当前每种角色最多一个账号，因此现阶段不支持同一长者绑定多个子女账号。

新家属账号的三项权限默认关闭，并保留“待长者重新授权”的初始历史。子女账号只是演示登录关系，不包含实名亲属关系核验。

## 5.2 登录、退出与账号切换

登录页提供三个角色入口，服务端校验账号角色与所选入口一致。登录成功后签发随机会话令牌，并通过 HttpOnly Cookie 保存。

退出时，服务端删除当前会话并清除 Cookie；前端清空业务数据、选中档案、筛选、资源推荐和批量选择状态，同时中止语音识别和播报。用户随后可重新选择老人、家属或社区入口登录其他账号。该机制支持同一浏览器顺序切换账号，不表示同一浏览器可同时保持多个账号并存。

## 5.3 四类业务状态流

| 业务 | 主要项目 | 状态流 | 办结要求 |
| --- | --- | --- | --- |
| 养老资格认证 | 社区人工核验、家属提交材料 | 待社区审核 → 审核通过 → 已完成 | 审核记录完整 |
| 高龄补贴 | 首次申请、补贴年审 | 待社区审核 → 审核通过 → 补贴发放中 → 发放完成 | 仅为本地状态演示，不代表实际到账 |
| 居家养老 | 助餐、助浴、保洁、陪护、理发修脚、维修、日照 | 待社区审核 → 已确认 → 已完成 | 完成说明必填，照片可选 |
| 老年体检 | 免费、慢病随访、普惠、慢病专项 | 待社区审核 → 已确认 → 已完成 | 办结后可手工录入演示报告 |

退回操作不直接按固定状态流推进，而是记录退回原因和补正历史。居家及体检预约还会校验未来时段、重复申请、资源启用状态和容量。

## 5.4 授权与数据裁剪流程

老人修改授权后，服务端保存权限和授权历史。后续状态请求由 `snapshot()` 按角色和权限重新生成：家属未获查看权限时不返回普通工单和探访；未获健康权限时不返回报告及健康敏感字段；未获代办权限时不能提交申请。该设计避免仅依赖前端隐藏按钮造成越权。

## 5.5 资源下架与改派流程

资源下架后，推荐、完整目录和新预约选项同步排除该资源。已经受影响且尚未办结的工单必须改派到类型匹配、启用且容量可用的资源后才能继续办理，避免下架资源仍被旧页面预约。

## 5.6 办结、报告与评价流程

居家工单办结必须填写完成说明，可补充服务照片；旧已办结工单允许补录结果。体检报告由社区手工录入，覆盖已有报告必须明确确认，并保留报告历史。老人和具备代办权限的家属只能对符合归属条件的已完成居家工单进行 1—5 分评价。

# 6 数据设计

## 6.1 数据模型概览

当前数据结构版本为 `schemaVersion: 2`，主要集合如下：

| 集合 | 主要内容 |
| --- | --- |
| `residents` | 长者姓名、出生日期及估算标记、画像、家属权限、授权历史和个人期限 |
| `accounts` | 账号 ID、用户名、角色、关联长者 ID、密码派生材料 |
| `cases` | 业务类型、项目、申请人、状态历史、预约资源、附件、完成说明、评分和报告 |
| `resources` | 服务类型、类别、项目、演示费用、电话、地址、容量、示意坐标和启用状态 |
| `visits` | 探访和关怀记录 |
| `resolved` | 服务超时预警处置记录 |
| `auditLog` | 部分管理动作的对象、经办人、时间和脱敏说明 |
| `hotline` | 社区服务热线配置 |

## 6.2 关键关联

- `accounts.elderId` 将老人或家属账号关联到唯一长者档案。
- `cases.elderId` 将工单归属到长者，`byAccount` 记录实际提交账号。
- `cases.resourceId` 记录预约资源，同时保存资源名称快照。
- `residents.family` 保存当前授权，`familyHistory` 保存授权变更历史。
- 工单 `history`、报告 `reportHistory` 和预警 `resolved` 分别承担业务过程留痕。

## 6.3 持久化、迁移与备份

保存时先写入临时文件，再重命名为正式数据文件，降低单文件写入中途失败的风险。旧版顶层画像、授权和期限数据可迁移到多档案结构，保留旧工单归属。

临时文件重命名不等于自动备份系统。当前备份主要来自重要操作前的人工或过程备份，其中 `nuanlin-data.backup-demo-cases-20261126.json` 仅包含演示长者工单及相关审计的专项备份，不是完整数据库副本。

截至本次修订，正式数据包含 4 份长者档案、7 个账号、2 条工单、7 条启用资源和 10 条审计记录。4 份档案包括“演示长者”旧档案以及王阿姨、李叔叔、孙阿姨三份新增档案；7 个账号包括 1 个社区账号、3 个老人账号和 3 个家属账号。

# 7 接口设计

## 7.1 基础接口

| 方法与路径 | 用途 | 主要约束 |
| --- | --- | --- |
| `GET /api/health` | 返回服务名和构建标识 | 本机 Host 校验 |
| `GET /api/setup` | 查询是否需要初始化 | 无有效社区账号时进入初始化流程 |
| `POST /api/setup` | 创建首个社区账号 | 需要当前进程随机初始化码 |
| `POST /api/session` | 登录 | 校验用户名、密码和角色入口 |
| `POST /api/logout` | 退出 | 删除当前会话并清除 Cookie |
| `GET /api/state` | 获取业务快照 | 按角色、权限、日期和选中长者裁剪 |
| `POST /api/action` | 执行业务变更 | 需要有效会话并通过角色 action 白名单 |

## 7.2 主要业务动作

`POST /api/action` 通过 `action` 字段区分申请、家属授权、画像维护、审核、资源改派、资源维护、探访、设置、档案、账号、密码、预警处置、结果录入和评价等操作。社区、老人和家属各自只能执行白名单内的动作。

## 7.3 请求与错误处理

- 请求体要求 JSON，大小限制约 1.1MB。
- 图片附件只接受规定格式的 JPEG Data URL，浏览器端先压缩尺寸和体积。
- 会话失效返回 401，前端回到登录页。
- 角色不匹配、权限不足、状态冲突、容量不足和资源不可用均返回明确错误。
- 审核和改派使用期望状态校验，防止并发覆盖。

# 8 安全与权限设计

## 8.1 密码与登录保护

密码使用独立随机盐的 scrypt 派生，并通过时间安全比较函数校验。用户名限制为 3—32 位小写字母、数字、下划线或短横线，密码长度为 8—128 位。登录失败按用户名和来源地址计数，在 10 分钟窗口内失败 5 次后阻塞 10 分钟。

## 8.2 会话安全

会话保存在服务端内存中，有效期 8 小时，Cookie 设置 `HttpOnly`、`SameSite=Strict` 和 `Path=/`。会话总量上限为 200，超过时淘汰最早会话。服务重启后所有会话失效。修改密码会撤销该账号其他会话，社区重置密码会撤销目标账号全部会话。

## 8.3 请求边界

服务只接受本机 Host；请求带 Origin 时必须与对应本机 HTTP 地址一致。静态资源采用白名单，响应设置 `X-Content-Type-Options: nosniff`；JSON 响应设置 `Cache-Control: no-store`。

## 8.4 审计与敏感信息

全局审计会剔除密码、散列、盐、令牌、附件、报告、出生日期和电话等敏感字段。并非所有操作都进入统一审计：登录、退出、申请、授权、探访、结果录入、评价和预警核销等部分操作主要通过各自业务历史留痕。因此，当前审计机制应描述为“全局管理审计与业务过程留痕并存”。

## 8.5 安全边界

当前没有 HTTPS，Cookie 未设置 `Secure`；没有独立 CSRF 令牌、加密数据库、持久化安全日志或生产安全认证。登录限速和会话都在内存中，重启会重置。系统仅适合作为本机演示，不能直接暴露到公网或用于真实敏感养老数据。

# 9 界面与适老化设计

## 9.1 角色化界面

老人和家属端强调大入口、清晰状态、语音辅助和较少操作步骤；社区端强调筛选、批量处理、统计和台账。页面支持标准、夜间和高对比度配色，并提供桌面及移动布局。

## 9.2 语音辅助边界

Web Speech API 的可用性取决于浏览器和操作系统。已有浏览器验收只证明朗读对象创建、播放或等待状态以及控件调用，不代表扬声器听感验收。麦克风权限被拒绝时提供文字降级路径；没有真实麦克风转写成功记录，也没有方言识别模型或方言纠错能力。浏览器语音识别可能使用浏览器厂商服务，不应描述为完全离线。

## 9.3 当前样式待复核项

当前样式文件在既有浏览器验收报告生成后发生变化。响应式字号与旧的固定 20px、22px、16px 断言不再一致，且三档字号依赖的 `--font-scale` 当前没有实际消费点。后续应统一“适老化目标、当前视觉设计和验收断言”，完成桌面、手机、三端角色及退出后的字号回归测试。

# 10 部署与运行说明

## 10.1 环境要求

- Windows 本机环境。
- Node.js 22 或更新版本，当前环境使用 Node.js 24.22.3。
- 推荐通过 `start.cmd` 启动；浏览器验收使用本机 Edge。

## 10.2 启动步骤

1. 双击项目根目录 `start.cmd`。
2. 保留启动终端，等待服务就绪并自动打开浏览器。
3. 默认访问 `http://127.0.0.1:8765/yanglao.html`。
4. 若 8765 被其他服务占用，启动器会选择后续端口，以终端显示地址为准。
5. 停止服务时在启动窗口按 Ctrl+C。

也可在项目目录执行 `node server.js`。不要通过 `file://` 直接双击 HTML 进行登录或保存数据。

## 10.3 数据与恢复

正式数据默认使用 `nuanlin-data.json`。恢复备份前必须停止服务，并另存当前文件，避免覆盖后续业务数据。验收和手动测试应通过 `NUANLIN_DATA` 使用隔离文件，不应把正式服务指向验收数据。

# 15 结论

暖邻平台已形成较完整的本机养老服务演示闭环，覆盖三类角色、四类业务、家属授权、资源运营、审核留痕、提醒统计和账号切换。通过 `yanglao.html` 路由统一，启动入口已得到修复；通过社区端语音和资源展示定制，三端界面职责更加清晰；通过三组老人及子女家属账号，可演示本人办理、授权代办和社区审核之间的关系。

当前版本的主要价值在于业务流程展示、交互验证和后续技术迭代。后续应优先修复字号缩放与验收一致性，完善审计和备份，再在明确隐私、安全和供应商接口规范的前提下推进真实外部服务接入。未完成这些工作前，系统应保持本机演示定位，不用于真实资格认定、资金发放、健康诊断或生产数据处理。
